# Многопоточность физики в Torque Foundry

Архитектурный документ. Статусы: **ПРИНЯТО** — решение зафиксировано, внедрение
по фазам · **ОБСУЖДЕНИЕ** — API-скетч, детали могут поменяться до внедрения.

Связанные документы: `Physics in Torque Foundry.md` (физическая модель),
`README.md` (игрок).

---

## 1. Цели

1. Физика не стоит на пути серверного тика: сервер отдаёт снапшот групп и
   возвращается к работе, воркеры считают параллельно.
2. Тяжёлые машины (металлургический комплекс: CALPHAD-интерполяция,
   многостадийная симуляция) **не замедляют** ни тик физики, ни сервер.
3. Аддон-разработчик получает понятный контракт: «что можно звать, откуда
   и что при этом гарантировано» — без чтения внутренностей движка.

Не-цели: параллелизм внутри одной группы (фазы A→B→C→D строго
последовательны — параллелить нечего), реентерабельность групп,
lock-free оптимизации до появления доказанного contention.

---

## 2. Три контура исполнения

```
серверный тред (20 TPS)
  ├─ топология: создание/слияние/распад групп, пакеты клиенту
  │   (единственный владелец Level и всего, что с ним связано)
  └─ PhysicsPipeline.tick(): снапшот групп → раздать воркерам →
     await прошлого тика → дренаж лёгких mailbox-заявок → вернуть

пул физики (N воркеров, 20 TPS, общий барьер)
  ├─ воркер: пачка групп; каждая группа тикает ЦЕЛИКОМ одним воркером
  ├─ группа НЕ может выполняться параллельно сама с собой (инвариант I1)
  └─ барьер по завершении всех групп слота

тяжёлый контур (0.2–1 TPS, свой ScheduledExecutorService)
  └─ HeavySimulation машин считает долго, публикует volatile-снапшот,
     никого не ждёт и не останавливает
```

Читатели данных физики (синк клиенту, рендер, оверлей) работают только со
снапшотами (§4) — никогда с живыми машинами напрямую.

---

## 3. Инварианты (жёсткие правила)

- **I1 — группа неделима.** Одна `MechanicalGroup` в пределах глобального
  тика выполняется ровно одним воркером ровно один раз. Scratch-буферы
  группы не защищены замками — их защищает этот инвариант.
- **I2 — состояние группы трогает только владелец.** Все прочие (другие
  группы, серверный тред, аддоны) — через снапшот (чтение) или mailbox
  (мутация/действие).
- **I3 — Level только с серверного треда.** Из пула физики запрещено
  что-либо вызывать на `Level`/`BlockEntity`/блоках. BE-тики делают
  топологию и синк, физика — только математику машин.
- **I4 — никакой ссылки на внутренности снапшота.** Читатель берёт
  `copyTo(view)` под замком и дальше работает со своим view. Сохранённая
  ссылка на массив из `front` — гонка.
- **I5 — тяжёлый код вне барьера.** В `computeTick()` и в mailbox-заявках
  нет ничего дороже микросекунд. Всё тяжёлое — в отдельный контур (§6).
- **I6 — лаг в 1 тик — норма.** Читатели видят «последний опубликованный»
  тик, не дожидаясь текущего. Консистентность (все поля из ОДНОГО тика)
  обязательна; свежесть последнего тика — нет.

## 4. Протокол снапшота (double-buffer из переиспользуемых объектов)

На группу три сущности, все предаллоцированы, ноль `new` в тике:

```
back   — черновик. Пишет ТОЛЬКО владелец группы (воркер) в конце тика.
front  — «последний тик». Публикуемое. Пишет только владелец, только под
         snapshotLock, одним куском. Читают все.
view   — per-reader переиспользуемый буфер (не на группу, а на читателя).
         Читатель копирует front → view под замком, дальше работает
         без замка.
```

**Публикация** (конец `computeTick()`, вне фаз A–D):

1. воркер дотикал группу — живые машины уже содержат новое состояние;
2. `snapshotLock.lock()` → скопировать скаляры и массивы в `front`,
   `tickId = simTick` → `unlock()`.

**Чтение:**

1. `snapshotLock` — серверный тред: блокирующе; рендер-тред: `tryLock()`,
   не взял — работает по view прошлого кадра (протухание на 1 кадр
   незаметно, рендер никогда не ждёт физику);
2. скопировать `front` → свой `view`;
3. отпустить замок; работать с `view` сколько угодно.

**Выбор механизма:** `ReentrantLock` на группу (одно поле). Альтернативы
`(synchronized` — нет `tryLock`; seqlock/swap-буферы — сложнее, переходить
только по доказанному профайлером contention). Голый `volatile` недостаточен:
видимость ссылки ≠ согласованность полей — публикация целиком под замком.

**Состав снапшота:** `currentSpeedRaw`, `simTick` (как `tickId`),
массив `WorkState` по машинам, `received`-мощности, тепло/температуры —
всё, что читают синк/оверлей/рендер. Публикация каждый тик всегда;
флаг `snapshotNeeded` (on-demand) — только по показаниям профайлера.

## 5. Mailbox: межгрупповые мутации через очередь

Группы независимы по построению, поэтому прямой межгрупповой доступ
в физике запрещён. Разрешено два канала:

- **Чтение чужого состояния** — из чужого `front`-снапшота (`tryLock`,
  скопировать во view). Заявка не нужна.
- **Мутация/действие над чужой группой** — только через mailbox:

```
GroupTask = { targetGroupId, op, payload (примитивы), replyBox }
postTask(target, op, ...)   — можно с любого треда, ставит в очередь
drainTasks()                — только владелец группы, после барьера
```

Исполнитель заявок (фаза дренажа, ПРИНЯТО для v1): **серверный тред** в
`PhysicsPipeline.tick()` после `awaitAll()` — он и так ждёт физику, заявки
редки и лёгки, один тред = детерминизм. Перенос дренажа на воркеров после
барьера (`Phaser`) — по росту нагрузки, не сейчас.

Ответ (replyBox) читается владельцем-отправителем в СВОЁМ следующем тике:
лаг в 1 тик, согласован с I6. Вложенные заявки (заявка из заявки) —
запрещены: дренаж не порождает новых заявок (иначе нет завершаемости).

## 6. Тяжёлый контур (HeavySimulation)

Машина с дорогой симуляцией НЕ тикает в `computeTick()` и не ходит через
mailbox. Она объявляет тяжёлый контур:

```
HeavySimulation {
    schedule(long periodTicks);       // свой темп, не 20 TPS
    Snapshot pollLatest();            // группа читает за volatile-read
}
```

- тяжёлый тред считает в своём темпе (раз в 20–100 тиков), публикует
  снапшот (volatile/atomic, свой double-buffer);
- группа в фазе A читает последний снапшот (кэшированные момент/КПД/
  потребление) за наносекунды;
- тик физики и сервер никогда не ждут тяжёлый тред.

Это третий контур в иерархии лагов: сервер → физика (лаг 1 тик) →
тяжёлая симуляция (лаг = её период). Для металлургии секунда лага
неотличима — печка и так «думает».

---

## 7. Контракт тредов (шпаргалка)

| API | Серверный тред | Воркер физики | Тяжёлый тред | Рендер/клиент |
|---|---|---|---|---|
| `Level`, `BlockEntity`, блоки, `BlockState` | да | **запрещено** | **запрещено** | только чтение в кадре |
| `MechanicalGroupManager` (топология) | да | нет | нет | нет |
| живые машины группы (`machine.*`) | нет | только своя | нет | нет |
| снапшот `front` (через `copySnapshotTo`) | да (блокирующе) | только своя back | нет | да (`tryLock`) |
| `postTask` (mailbox) | да | да | да | нет |
| `drainTasks` | да (v1) | нет | нет | нет |
| `HeavySimulation.pollLatest` | да | да | пишет | да |
| хуки `PhysicsHook` | — | как объявлено в хуке (см. §8) | — | нет |

## 8. Публичный API (ОБСУЖДЕНИЕ, скетч v1)

Пакет: `dev.sdm.torque_foundry.api.physics`. Принцип: **всё, что может
позвать аддон, аннотировано тредовым контрактом** — раз у нас нет
проверки в рантайме, контракт должен быть виден в сигнатуре.

### 8.1 Чтение: снапшоты

```java
/** НЕИЗМЕНЯЕМЫЙ снаружи view; копия под замком. */
public final class GroupSnapshotView {
    public long groupId();
    public long tickId();                 // какой тик опубликован
    public int machineCount();
    public long netSpeedMilliRpm();
    public WorkState state(int index);
    public long receivedWatts(int index);
    // ... набор растёт по потребности читателей
}

public final class PhysicsReads {         // стatical-фасад чтения
    /** Любой тред. Копирует front группы во view читателя. */
    public static boolean copySnapshot(long groupId, GroupSnapshotView into);
    /** Рендер: не блокирует, false = берите прошлый view. */
    public static boolean tryCopySnapshot(long groupId, GroupSnapshotView into);
}
```

View — обычный mutable POD, читатель держит один экземпляр и переиспользует
(в рендере — поле, в синке — локальная переменная цикла).

### 8.2 Действие: mailbox

```java
public interface GroupTask {
    /** Выполняется ВЛАДЕЛЬЦЕМ группы после барьера (сервисный тред). */
    void execute(MechanicalGroup owner, GroupTaskContext ctx);
}

public final class PhysicsTasks {
    /** Любой тред. Задача исполнится владельцем в текущем цикле дренажа. */
    public static void post(long groupId, GroupTask task);
}
```

`GroupTaskContext` — узкое окно к живой группе: читать машины, менять
конкретные поля через специфицированные методы. Прямого доступа к массиву
машин нет — только методы контекста (контроль инварианта I2 одной точкой).

### 8.3 Тяжёлая машина

```java
public interface HeavySimulation {
    /** Период тяжёлого тика в тиках физики (>= 20). */
    int periodTicks();
    /** Вызывается в тяжёлом треде. Level недоступен (I3). */
    HeavyResult computeHeavy(HeavyInput input);
    /** Что группа видит в следующем тике (volatile-read). */
    HeavySnapshot latest();
}

// регистрация — из машины при создании:
machine.setHeavySimulation(new MyAlloySim(...));
```

`HeavyInput` — тоже снапшот (копия нужных полей), не живые машины.

### 8.4 Существующие хуки `PhysicsHook`

Подписи не меняются, добавляется документ-контракт: все хуки вызываются
в треде воркера, владеющего группой; внутри хука запрещено касаться
`Level` и чужих групп (I2, I3). Хуки, которым нужны данные соседей, —
через `PhysicsReads`/`PhysicsTasks` на общих основаниях.

### 8.5 Что НЕ входит в API

- `MechanicalMachine`, `MechanicalGroup`, scratch-буферы — внутренние.
  Аддон-машина наследует `MechanicalMachine`, но зовёт только хуки и
  публичный API выше.
- Никаких `ExecutorService` наружу: пулы — внутренность движка.

## 9. Фазы внедрения

1. **Ф1 — ГОТОВО:** `GroupSnapshot`/`GroupSnapshotView`,
   `snapshotLock`, публикация в конце `computeTick()`. Стресс-тест на
   согласованность по `tickId` (`SnapshotConsistencyTest`). Снапшот
   сохраняет слоты машин (индекс = слот), дыры топологии — `posLong = 0`.
   Читатели (оверлей/инспектор) пока читают клиентские копии — их перевод
   на view уйдёт вместе с клиентским синком.
2. **Ф2 — ГОТОВО:** mailbox `PhysicsTasks.post` + дренаж в серверном треде
   (`PhysicsPipeline.tick()` после барьера, до пробуждения воркеров);
   `GroupTask`/`GroupTaskContext`; изоляция исключений в задачах;
   **синк клиенту переведён на снапшот** (`TFNetworking.buildPayload`
   копирует `front` под замком — гонка «сервер читает машины, физика их
   мутирует» закрыта; payload собирается из view, буфер переиспользуется).
3. **Ф3 — ГОТОВО:** пул воркеров вместо выделенного потока. `tick()`
   сабмитит слоты в `ExecutorService` и возвращается (Future.get на
   СЛЕДУЮЩЕМ тике — семантика опережения сохранена, спин-лок убран).
   Балансировка — жадная each-to-least-loaded по `getSize()`, O(g·t),
   детерминирована, без сортировок и аллокаций (scratch-буферы пайплайна).
   Пул в `MechanicalGroupEvents`: `availableProcessors()/2`, зажато в
   1..4, потоки-демоны `TorqueFoundry-Physics-N`, `shutdownNow` при
   остановке сервера. Отказ слота изолирован: `ExecutionException`
   логируется, остальные слоты тикаются, сервер не виснет.
4. **Ф4:** `HeavySimulation` + тяжёлый контур (к моменту металлургии).
5. **Ф5 (по необходимости):** `snapshotNeeded`, дренаж на воркерах,
   seqlock вместо замка — только по профайлеру.

---

## 10. Решения (зафиксировано)

- **Фасады:** `PhysicsReads` + `PhysicsTasks` — раздельные фасады чтения
  и задач, не один общий вход.
- **Язык JavaDoc публичного API:** русский (единообразие с проектом).
- **Состав `GroupSnapshotView` v1:** полный, как читает оверлей — скорость
  сети, `WorkState`, received-мощность, тепло/температуры, derate,
  подшипники/смазка. Обратная совместимость: новые поля только добавлением,
  читатели ходят индексно — добавление не ломает аддоны.

Внедрение — по фазам §9, начиная с Ф1.
