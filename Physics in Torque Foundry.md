## Базовые компоненты

Начало физики берёт от материалов — они управляют основными показателями
(ГОТОВО: record PhysicsMaterial, 17 полей, 4 группы):
1. Масса и инерция: плотность (kg/m³) — масса детали по объёму, инерция сети
2. Упругость/жёсткость: модуль сдвига G, модуль Юнга E, коэффициент Пуассона ν
3. Пределы прочности: текучести (σ_y растяжение, τ_y сдвиг), временное
   сопротивление σ_u, усталостная прочность σ-1, твёрдость HB
4. Трение и теплофизика: коэффициент трения μ, тепловое расширение α,
   теплоёмкость c, теплопроводность λ

### Философия данных: независимое задаём, зависимое выводим (ГОТОВО)

В материале задаются ТОЛЬКО независимые физические константы. Зависимые
выводятся автоматически по формулам сопромата (Builder):
- G = E / (2(1+ν))                      [оверрайд для анизотропии — дерево]
- τ_y = σ_y / √3                        (критерий текучести фон Мизеса)
- σ-1 = k_fatigue · σ_u                 (эмпирическая оценка выносливости;
  k_fatigue — КОЭФФИЦИЕНТ СЕМЕЙСТВА материалов: сталь 0.45, чугун 0.40,
  бронза 0.35, дерево 0.35. Соотношение 0.45 валидно только для сталей:
  у алюминия настоящего предела выносливости нет вообще (кривая усталости
  не выходит на горизонталь), у меди/дерева коэффициент другой. Хардкод
  одной константы на все семейства при CALPHAD-интерполяции даст системную
  ошибку — поэтому коэффициент наследуется от архетипа и переопределяется.)

Игровая динамика не хранит отдельных полей, а потребляет физику через
производные методы (ГОТОВО):
- инерция сети = ρ / 7850 × 2
- трение сети = μ / 15
- безопасные обороты = 256 · √(σ_y / σ_y_стали)   [Допущение — см. ниже]

Плюс: поменял физику — игровой баланс сдвинулся сам, рассинхрон невозможен.
Архетипы Builder'а (steel / wood / bronze / castIron) задают типовые
константы семейства — новый материал = 3-4 цифры.

Пресеты: WOOD (дуб), BRONZE (оловянистая), IRON (серый чугун), STEEL
(конструкционная) — справочные значения при 20 °C.

### Допущение: безопасные обороты без плотности (сознательное упрощение)

Реальный физический потолок вращения — центробежный разрыв: напряжение
σ ∝ ρω²r², откуда ω_max ∝ √(σ_y/ρ). Наша формула нормирует только прочность,
без плотности. Разлад: дерево лёгкое (центробежная нагрузка мала), и по
«чистой» физике могло бы крутиться быстрее стали. Плотность опущена
СОЗНАТЕЛЬНО: игровой износ моделирует поверхностную усталость и износ
опор, а не разрыв обода; на игровых радиусах центробежный разрыв недостижим.
Последствия: относительный порядок материалов (дерево < чугун < бронза <
сталь) сохранён, абсолютные числа — игровые. Когда появится геометрия
деталей, добавить второй лимит: burstRPM(r) ∝ √(σ_y/ρ)·1/r и брать
min(прочностной, центробежный). До тех пор формула — игровой баланс, а не
физический предел (маркировать при любых правках).

### Металлургия сплавов CALPHAD (ПЛАН)

Материалы модульны и легки в настройке: в будущем металлургия сплавов по
пропорциям через CALPHAD (расчёт термодинамических диаграмм фаз) позволит
создавать сплавы динамически. Схема: игрок задаёт пропорции компонентов ->
физические свойства ИНТЕРПОЛИРУЮТСЯ (плотность, E, σ_y, μ, c...) -> всё
зависимое выводится существующим Builder'ом автоматически -> PhysicsMaterial
собирается на лету. Требование к коду: материал — иммутабельные данные,
никаких ссылок на зарегистрированные пресеты внутри машин (соблюдается).

Для выбора сплавов у механизмов будут требования-спеки: «этому узлу нужно
σ_u >= N, λ >= A» — по ним игрок решает, какой сплав где применять (ПЛАН).

## Механические цепочки

### Валы (ЧАСТЬ)

Два вида вала (ГОТОВО):
1. **Вал-блок** (ShaftBlock): самостоятельный блок-сегмент сети, материал
   меняется Shift+ПКМ (WOOD..STEEL), 2 опорные точки (подшипники),
   тир балансировки при установке.
2. **Вал-вставка шасси** (ГОТОВО): предмет «Вал» (DataComponent
   `shaft_material`, 4 материала) вставляется в шасси — шасси становится
   проходным сегментом вала IN_OUT по оси FACING. Материал вставки =
   трение/инерция/лимит износа; износ применяется тем же ShaftWearHook
   (isShaftSegment). Ядро шасси — шестерня ИЛИ вал, взаимоисключаемо,
   извлекается ключом. Опорные точки у вал-вставки отсутствуют
   (упрощение MVP — опоры у полноценных вал-блоков).

- Предел крутящего момента: T_max = (π r³/2) · τ_y / k (ГОТОВО, r=0.025, k=2;
  превышение — пластические потери ~1%/превышение, двукратное — срез)
- Скоростной лимит: износ выше безопасных оборотов материала,
  ~1% × (превышение/лимит) на каждый вал пути (ГОТОВО)
- Нагрев (ГОТОВО: трение -> тепло)
- Собственная инерция: пока константа материала; далее ½mr² по геометрии (ЧАСТЬ)
- Центровка/балансировка Grade C/B/A/S (ГОТОВО для вал-блока — см. ниже;
  для вал-вставки шасси — ПЛАН)
- Длина пролёта без опор (ПЛАН): непрерывные цепочки валов для обслуживания

### Опоры и смазки (ЧАСТЬ: физика и предметы ГОТОВО, рецепты/трубы ПЛАН)

Вал держится в двух опорных точках (торцы по оси). Реализовано 3 типа из 5:
1. Втулка SLEEVE: рейтинг 500 RPM, множитель трения 0.85 (ГОТОВО)
2. Роликовый ROLLER: 1500 RPM, 0.70, требует смазку (ГОТОВО)
3. Шариковый закрытый BALL: 2500 RPM, 0.50, смазки не требует (ГОТОВО)
4. Опоры (очень малые скорости) — ПЛАН
5. Конические/упорные (500-1500 RPM, масляная ванна) — ПЛАН

Механика (ГОТОВО):
- Без подшипника — «голый упор» шасси: работает, множитель трения 1.0
- Подшипник — предмет, ставится ПКМ по торцу вала, хранится в BlockEntity,
  снимается гаечным ключом (возвращается предметом)
- Износ ∝ (RPM/рейтинг)²: в пределах рейтинга — почти вечный, превышение —
  быстрый износ. Отказ: трение хуже голого упора (×1.8), опора сама пустеет
- Смазка: резервуар машины (1000 ед.), 2 типа предметов (GREASE/OIL,
  механически эквивалентны — разделятся с температурными лимитами),
  расход ∝ оборотам × числу опор; пустой бак = трение деградирует к голому
  упору + износ ×3 (только опорам, требующим смазки)

ВАЖНО: подшипник и смазка — это МОДИФИКАТОРЫ узла, а не отдельная физика:
- смазка -> множитель μ узла и множитель предельной температуры
- несоответствие RPM-рейтингу -> множитель нагрева и износа

### Балансировка вала: Grade C/B/A/S (ГОТОВО)

Тир предмета вала задаётся качеством станка при крафте (верстак = C,
станок = B, лазерный = A, технологический = S; станки — ПЛАН, сейчас все
скрафченные валы — Grade C через DataComponent `shaft_grade`).

Тир -> стартовый перекос вала при установке:
- Grade C = 2.0°: трение +100%, износ +200%
- Grade B = 1.0°: трение +50%, износ +100%
- Grade A = 0.5°: трение +25%, износ +50%
- Grade S = 0.1°: практически идеальная центровка

Перекос хранится на весь вал (одно число). Ручная докалибровка
(поднять показатели готового вала) — ПЛАН.

### Шасси и кастомные шестерни (ЧАСТЬ: физика и предметы ГОТОВО, рецепты/текстуры ПЛАН)

- Шасси — блок-контейнер со СЛОТОМ ЯДРА: шестерня ИЛИ вал-вставка
  (взаимоисключаемо). Для шестерни: вход (задняя грань относительно
  FACING) / выход (FACING); вал-вставка делает шасси проходным по оси
  FACING. Пустое шасси мощность не проводит. Вставка ПКМ, извлечение
  гаечным ключом, замена — старое возвращается в инвентарь. Ядро
  сохраняется между перезапусками.
- Шестерня — ПРЕДМЕТ: число зубьев (DataComponent `gear_teeth`, из размера
  заготовки при крафте) + физический материал (`gear_material`).
- Рейтинги выводятся из физики (ГОТОВО):
  рейтинг момента = T_max материала на радиус делительной окружности
  (радиус растёт с зубьями — крупная шестерня держит больше);
  рейтинг оборотов = безопасные обороты материала (усталость поверхности).
- Зацепление: шестерня сцеплена с приводной шестернёй шасси (8 зубьев):
  n = 8 / зубья. Больше зубьев — ниже обороты, выше момент. Внешнее
  зацепление реверсирует вращение.
- Превышение рейтинга момента/оборотов — потери КПД ~1% на превышение
  (шестерня «жует» мощность).
- GUI-сборка целых коробок — приоритет 10.

[ОТЛОЖЕНО: модуль зацепления, эвольвентный профиль, угол зацепления —
игрок их не увидит; весь расчёт сведён к рейтингам момента/оборотов.
Изнашиваются все зубья сразу, не по одному — по одному дорого.]

## Механизмы

Спеки механизма (все в СИ; в движок — конверсия на границе).
Все поля ниже реализованы как переопределяемые методы MechanicalMachine
(ГОТОВО как механизм; пресеты значений на машинах — по мере баланса):

public record MachineOperationalSpec(
    // Силовые пороги
    double minBreakawayTorqueNm, // Момент страгивания: ниже — машина не
                                 // стронется и заклинит сеть (ГОТОВО:
                                 // getBreakawayTorqueRaw, потребитель
                                 // страгивается своим рабочим моментом)
    double minSpeedRpm,          // Минимальные обороты полезного действия (ГОТОВО: required)

    // Инерция и холостой ход
    double rotorInertiaKgM2,     // Инерция ротора: + к инерции сети (ГОТОВО:
                                 // getExtraInertia)
    double idleTorqueNm,         // Потери холостого хода (ГОТОВО:
                                 // getIdleTorqueRaw в loadTorque)

    // Тепло и КПД
    double efficiency,           // КПД: P_loss = P_in * (1 - eta) -> в тепло
                                 // корпуса машины (ГОТОВО: getEfficiency +
                                 // applyEfficiency в фазе A)
    double maxTemperatureC,      // Порог деградации (ГОТОВО для генератора:
                                 // тепловой derate; прочим машинам — ПЛАН)

    // Монтаж (дешёвая версия)
    double maxShaftMisalignmentDeg // Перекос: множитель трения+износа (ГОТОВО:
                                   // Grade тир вала -> misalignmentDeg)
) {}

[ОТЛОЖЕНО: torqueRippleFactor и vibrationEmissionRate — вибрации без
рендера/звука неощутимы; вернуться, когда появится на что смотреть.]

### Генераторы

- Выходные параметры: номинальные обороты/момент/мощность, предельные
  обороты (ГОТОВО: 256 RPM / 64 Nm базовый; конструктор с η и пределом
  температуры)
- Тепловые ограничения (ГОТОВО): потери P_out·(1-η)/η греют ротор; выше
  предельной температуры момент линейно derate'ится до пола 0.3
  (onSourceTick -> SimulationState -> getOutputFactor)
- Режим работы S1-S8 — ГОТОВО как эмерджентное поведение: НЕ таймерами,
  режим ВОЗНИКАЕТ из тепловой модели. Перегруз -> нагрев ротора
  (теплоёмкость поглощает пик = S2) -> при предельной температуре derate
  момента -> потребитель клинит -> скорость 0 -> потерь нет -> остывание
  -> восстановление. Тяга сети считается от DERATED момента (фаза B берёт
  вход фазы A, не паспорт) — иначе перегрев не останавливает нагрев.
- Поведение под нагрузкой: пусковой момент, опрокидывающий (пиковый)
  момент (ПЛАН)
- Радиальные/осевые нагрузки на вал (ПЛАН, вместе с опорами)

### Передачи (ГОТОВО — все как шаблоны)

- Коническая передача (η 0.96)
- Крестовой конический разветвитель (η 0.95)
- Механический дифференциал (η 0.97)
- Маховик (энергобуфер, свой циклический КПД)
- Коробка передач (η 0.95)
- Планетарный механизм (η 0.97)
- Раздаточная коробка (η 0.94)
- Червячная передача (η 0.75 — односторонняя, самотормозящая, не разветвитель)

Идеал — сборка авторских коробок игроком: «сборочная коробка» как
виртуальный узел (см. движок). Пока шаблоны полностью закрывают геймплей.

## Физика сети (ГОТОВО — фиксированные правила, не менять без обсуждения)

### Сеть — маховик

Все механизмы вплотную образуют сеть. Динамика сети — ОДНА скорость на
всю сеть (жёсткая сцепка): spin-up/плато/выбег считаются для скаляра
оборотов. Момент источника разгоняет сеть, трение тормозит:
- Разгон: инерция = сумма инерций всех ВРАЩАЮЩИХСЯ машин (+ роторы
  getExtraInertia)
- Равновесие: тяга источника = суммарному трению (f·RPM на машину) —
  длинная цепь «съедает» обороты (8 железных валов: 256 -> ~237 RPM)
- Выбег: после снятия источника сеть плавно останавливается трением
- Мёртвые ветви (за потребителем, куда мощность не доходит) не вращаются
  и сеть НЕ нагружают

[ОГРАНИЧЕНИЕ МОДЕЛИ — инерция без передаточных чисел. transform() на
ребре меняет передаваемую мощность (после КПП 1:2 на ребре видно
512 RPM / 16 Nm), но динамика сети — один скаляр: жёсткая сеть с КПП
физически противоречива. Правильная модель — ПОСТРОЧНЫЕ скорости ветвей
и приведённая инерция (reflected inertia): инерция поддерева за узлом
домножается на ratio² узла (энергия ½Iω², а не сам I) — тяжёлый барабан
за редуктором 1:10 ощущается источником в 100 раз тяжелее. Требует
перехода от скаляра сети к скоростям по рёбрам — большой отдельный кусок,
приоритет 11. До тех пор КПП меняет только раскладку момента/оборотов
на рёбрах, не динамику.]

### Перегруз: три случая (не смешивать!)

1. ЖЁСТКАЯ ПЕРЕГРУЗКА (ГОТОВО) — суммарный требуемый момент потребителей
   больше, чем источники дают в принципе. Мгновенный стоп + КЛИН всей
   цепи до источника. Заклинивший потребитель давит на сеть СТРАГИВАНИЕМ
   (max(рабочий, страгивание) — статическое трение), не давая
   раскрутиться обратно. Клин держится, пока перегруз не уйдёт.
2. МАРГИНАЛЬНЫЙ ДЕФИЦИТ (ГОТОВО) — момент потребителя посильный, но
   трение на высоких оборотах съело запас. Сеть НЕ встаёт: плавное
   торможение, потребитель отключается, разгон — устойчивая «пила» у
   порога включения. Мгновенное обнуление здесь давало вечный цикл
   разгон->порог->ноль (баг был, починен — не возвращать).
3. КОНФЛИКТ НАПРАВЛЕНИЙ (ГОТОВО) — слияние допускает несколько родителей.
   Источники с РАЗНЫМ направлением вращения гасят друг друга (момент уходит
   в тепло/клин), а не складываются (раньше это был эксплойт: два встречных
   генератора удваивали тягу). Знак-учёт в ДВУХ местах: слияние inputPower
   (Σ signed, более сильный встречный поток переориентирует узел) и тяга
   сети в фазе B (опорное направление = первый источник). Класс — жёсткая
   перегрузка (третий триггер клина).

   ГИСТЕРЕЗИС (ГОТОВО, обязательно сохранить): клин только при N=20 тиков
   ПОДРЯД устойчивого конфликта. Это лекарство от того же класса дребезга,
   что был в маргинальном дефиците: при net_torque ≈ 0 remainder-округление
   качает его вокруг нуля — без гистерезиса получили бы флип клин<->не-клин
   каждый тик. Один механизм гистерезиса на оба случая.

### Износ

Теряется МОМЕНТ (КПД), не обороты:
- Валы, обороты выше безопасного лимита материала: ~1% × (превышение/лимит)
  на каждый вал пути (ShaftWearHook)
- Валы, момент выше T_max: пластические потери; двукратное превышение — срез
- Подшипники: износ ∝ (RPM/рейтинг)², отказ опоры — трение ×1.8 (см. Опоры)
- Шестерни: превышение рейтинга момента/оборотов — потери ~1%/превышение
  (см. Шасси)

### Нагрев (ГОТОВО)

- Трение -> тепло: P = τ_тр · ω, за тик E += P/20 (железный вал на
  256 RPM ~ 200 Вт)
- Температура: T = окружающая + E / (m·c); масса — номинальная деталь
  1000 см³, пока у машин нет геометрии (сталь 7.85 кг, дерево 0.7)
- Конвекция к среде: постоянная времени τ = c / k_охл, где
  k_охл = 8 Вт/(кг·К) — конвекция на килограмм массы. Размерность сходится:
  [Дж/(кг·К)] / [Вт/(кг·К)] = [Дж/Вт] = секунды (сталь ~58 с, дерево ~212 с —
  теплоёмкие остывают дольше, как в жизни). Допущение: k_охл прячет в себе
  отношение площади теплообмена к массе (A/m) эталонной детали 1000 см³ —
  для деталей сильно иной формы реальная конвекция уйдёт за допуск 10-15%.
  Уточнится автоматически, когда в модель войдёт геометрия (тот же пакет,
  что инерция по геометрии).
- Тепло живёт в машине (physics.machine.SimulationState): на нём строятся
  тепловой derate генератора (ГОТОВО), деградация от перегрева (ПЛАН),
  передача тепла между машинами и нагрев помещений (ПЛАН)
- КПД передач (ГОТОВО): P_loss = P_in(1-η) льётся в тот же addHeatJ

## Физический движок

Движок работает в ОДНОМ выделенном потоке, опережая тик сервера (кадровая
логика читает вчерашний результат — стабильно и без блокировок).
Разбивка групп по разным потокам — задел на будущее; имеет смысл только
при сотнях групп (закон Амдала: синхронизация съест выигрыш на мелких).

Механизмы группируются в группы по механической связности.

Группа — НАПРАВЛЕННЫЙ АЦИКЛИЧЕСКИЙ ГРАФ (DAG), не дерево: узлы могут иметь
несколько родителей (слияние от двух генераторов) и несколько детей.
Уровневая фильтрация режет обратные рёбра. Узлы изменения поведения —
transform() на каждой машине: после КПП одна ветка получит 512 RPM / 16 Nm,
другая останется 256 RPM / 32 Nm.

Сборочные коробки (ПЛАН, приоритет 10): коробка, собранная игроком из
валов и шестерён, для движка — виртуальный узел: подграф с одной точкой
входа и выхода, считается как одна машина с агрегированным transform().
Начало положено: шасси с одной шестернёй — простейший «виртуальный узел»
(см. Шасси); GUI-сборщик мультиступенчатых коробок — следующий шаг.

### Реализовано (1-9)

1. КПД: transform() теряет (1-η) -> addHeatJ — связывает передачи с
   нагревом. getEfficiency() на машине, applyEfficiency в фазе A;
   червячная 0.75, ремень 0.92, раздатка 0.94, коническая 0.96,
   КПП/крест 0.95, планетар/дифф 0.97

   гистерезис клина N=20 тиков
3. Момент страгивания: getBreakawayTorqueRaw(), фаза C INSUFFICIENT + клин;
   потребитель страгивается своим рабочим моментом
